# Day-21 — HybridCache + Stampede Protection

Added a two-tier **HybridCache** (in-memory L1 + Redis L2) to a hot read, with
**stampede protection** so a cache miss under concurrency does not fan out into
N identical DB queries. Below: the wiring, the load-test before/after, and the
proof that stampede protection works.

The hot read is the Day-11 perf endpoint `GET /api/authors/summary` — an EF
query over **50,000 rows** (200 authors × 250 quotes) that, per author, counts
non-deleted quotes and fetches the latest one. A covering index
(`IX_Quotes_AuthorId INCLUDE (IsDeleted, Text)`) is in place, so the baseline is
an already-optimized query — the cache still beats it decisively.

---

## 1. Cache wiring

**DI** — [`ServiceExtensions.cs`](QuotesApi/Extensions/ServiceExtensions.cs).
Registering an `IDistributedCache` (Redis) is what promotes HybridCache from
L1-only to the full two-tier cache:

```csharp
var redisConnection = configuration.GetConnectionString("Redis");
if (!string.IsNullOrWhiteSpace(redisConnection))
{
    services.AddStackExchangeRedisCache(options =>
    {
        options.Configuration = redisConnection;   // localhost:6379
        options.InstanceName  = "quotes:";
    });
}

services.AddHybridCache(options =>
{
    options.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration           = TimeSpan.FromMinutes(5),  // total TTL (L2)
        LocalCacheExpiration = TimeSpan.FromMinutes(5),  // L1 serve window
    };
});

services.AddSingleton<CacheMetrics>();   // tally to prove hit-rate / DB load
```

**The cached read** — [`PerfEndpoints.cs`](QuotesApi/Extensions/PerfEndpoints.cs).
`GetOrCreateAsync` is the whole story: L1 → L2 → factory (DB), and it coalesces
concurrent callers for the same key onto **one** factory execution.

```csharp
group.MapGet("/summary-cached", async (AppDbContext db, HybridCache cache,
                                       CacheMetrics metrics, CancellationToken ct) =>
{
    metrics.RecordRequest();
    var result = await cache.GetOrCreateAsync(
        "authors:summary",
        async token =>
        {
            metrics.RecordDbQuery();        // runs ONLY on a genuine miss
            return await db.Authors.AsNoTracking().OrderBy(a => a.Name)
                .Select(a => new AuthorSummaryDto(
                    a.Id, a.Name,
                    a.Quotes.Count(q => !q.IsDeleted),
                    a.Quotes.Where(q => !q.IsDeleted).OrderByDescending(q => q.Id)
                            .Select(q => q.Text).FirstOrDefault()))
                .ToListAsync(token);
        },
        cancellationToken: ct);
    return Results.Ok(result);
});
```

`dbQueries` is incremented **inside the factory**, so it counts real DB
round-trips. Hit rate = `1 − dbQueries / requests`. Read it at
`GET /api/authors/cache-stats`; `POST /api/authors/cache-reset` evicts the key +
zeroes the counters for a cold start.

**Infra:** Redis 7 + SQL Server 2022 via [`docker-compose.yml`](docker-compose.yml).
Load generated by two dependency-free .NET file-based apps:
[`Scripts/loadtest.cs`](Scripts/loadtest.cs) (sustained, closed-loop) and
[`Scripts/burst.cs`](Scripts/burst.cs) (N simultaneous requests).

## 2. Load test — before vs after

**50 connections, 15 s, same machine, same query, same data.**
"Before" = `/api/authors/summary` (no cache). "After" = `/api/authors/summary-cached` (warm).

| Metric                 | Before (uncached) | After (HybridCache) | Change            |
|------------------------|-------------------|---------------------|-------------------|
| Throughput             | **140 req/s**     | **4 588 req/s**     | **×32.8**         |
| Requests in 15 s       | 2 117             | 68 863              | —                 |
| **DB queries (total)** | 2 117 (1 per req) | **1**               | 68 863 served by 1 query |
| **DB queries / sec**   | **≈ 140**         | **≈ 0.07**          | **~2000× less load** |
| Cache hit rate         | 0 %               | **100 %** (68 863 / 68 864) | —         |
| p50 latency            | 296.8 ms          | **8.6 ms**          | ÷34               |
| **p99 latency**        | **985.1 ms**      | **29.2 ms**         | **÷33.7**         |
| max latency            | 3 346 ms          | 142 ms              | ÷23               |
| errors                 | 0                 | 0                   | —                 |

Raw output:

```
BEFORE — uncached /api/authors/summary
  requests   : 2117
  throughput : 140 req/s
  latency ms : p50=296.8  p90=599.0  p99=985.1  max=3346.5

AFTER — cached /api/authors/summary-cached  (warm)
  requests   : 68863
  throughput : 4588 req/s
  latency ms : p50=8.6  p90=19.2  p99=29.2  max=142.3
  server stats: {"requests":68864,"dbQueries":1,"servedFromCache":68863,"hitRatePercent":100}
```

The database went from carrying ~140 identical queries/sec to **one query total**
over the whole 15 s warm window — and clients got their answer ~34× faster at p99.

## 3. Stampede protection (the headline)

Fire **200 requests simultaneously** (`burst.cs`, `Task.WhenAll`) at a **cold**
key. Without protection all 200 miss together and each runs the query — 200 DB
hits. With HybridCache they coalesce onto a single factory execution.

| 200 simultaneous, cold cache | Wall-clock | p50      | max      | **DB queries** |
|------------------------------|-----------:|---------:|---------:|---------------:|
| Cached (stampede-protected)  | **256 ms** | 214 ms   | 230 ms   | **1**          |
| Uncached (`/summary`)        | 2 964 ms   | 1 051 ms | 2 922 ms | 200            |

```
COLD cache → 200 simultaneous → cached endpoint
  completed  : 200/200 OK in 256ms
  server stats: {"requests":200,"dbQueries":1,"servedFromCache":199,"hitRatePercent":99.5}

Same burst → UNCACHED endpoint (no coalescing)
  completed  : 200/200 OK in 2964ms   (p50=1051ms, max=2922ms)  → 200 DB hits
```

**200 concurrent cache misses collapsed to a single DB query**, and the burst
finished ~12× faster because the DB was never stampeded.

---

## 4. The L2 (Redis) tier is real

Proof that this is two-tier and not just in-memory: **restart the API process**
(wipes the in-memory L1) — the Redis L2 entry survives, so the first request
after restart is served from Redis with **zero** DB queries.

```
Redis key after warm run : "quotes:authors:summary"  (TTL 255s)
→ restart API process (L1 gone)
→ first request to /summary-cached: HTTP 200
  server stats: {"requests":1,"dbQueries":0,"servedFromCache":1,"hitRatePercent":100}
```

`dbQueries = 0` on a brand-new process ⇒ the value came from Redis, not the DB.

## How to reproduce

```bash
docker compose up -d sqlserver redis
# run API (env overrides point at the local container + Redis):
#   ConnectionStrings__Default=Server=localhost,1433;Database=QuotesDb;User Id=sa;Password=YourStrong@Passw0rd;TrustServerCertificate=True;
#   ConnectionStrings__Redis=localhost:6379
dotnet run --project QuotesApi -c Release
curl -X POST "http://localhost:5005/api/authors/seed?authors=200&perAuthor=250"

cd Scripts
dotnet run loadtest.cs -- http://localhost:5005/api/authors/summary        50 15   # before
dotnet run loadtest.cs -- http://localhost:5005/api/authors/summary-cached 50 15   # after
curl -X POST http://localhost:5005/api/authors/cache-reset
dotnet run burst.cs    -- http://localhost:5005/api/authors/summary-cached 200     # stampede
curl http://localhost:5005/api/authors/cache-stats
```
